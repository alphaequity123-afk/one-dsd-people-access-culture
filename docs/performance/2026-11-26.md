# Search and page-loading performance

Baseline: `7cda443f` (main at the start of this work).

## Changes

- Validate current course-media manifests and required assets with eight bounded workers instead of a serial loop. Keep manifest order, malformed-file handling, retirement exclusions, file-size limits, and fresh reads for search/Ask.
- Read supplemental course captions/transcripts with the same bounded concurrency. Preserve parent-publication eligibility and content hashes.
- Rank search candidates before building excerpts. Generate excerpts only for displayed, deduplicated results. Match each excerpt by document kind, ID **and destination**, so reused IDs cannot attach another destination's text.
- Return content-free `Server-Timing` measurements for library preparation, supplemental material and ranking. Keep responses `no-store` and the existing JSON contract.
- Stream Home's calendar under Suspense, allowing the main content to render before community-publication checks finish.
- Skip the legacy text editor's page-wide index and mutation observer for ordinary readers with no saved edits. Retain saved wording/images, hydration handling and owner editing.

No cache lifetime was extended. In particular, a removed media manifest or missing required asset is still excluded by the next fresh read. No sources, content, voice settings, permissions or AI models were changed. Ask already has content-free stage timing; that instrumentation remains in place.

## Measured comparison

Read-only tests used a local Windows runner, the connected runtime database and Railway media bucket. Both implementations used the same source checkout and settings. This checkout includes the source/data required for tests, rather than every production static media asset. These are comparative measurements, **not deployed HTTP timings or load-test percentiles**.

| Operation | Before | After | Change |
| --- | ---: | ---: | ---: |
| Validate 49 published media items (median of 3) | 35,780 ms | 5,230 ms | 85.4% lower |
| Full search: leadership | 56,217 ms | 9,228 ms | 83.6% lower |
| Full search: accessibility | 37,068 ms | 7,009 ms | 81.1% lower |

The media comparison asserted equality of every returned item, not just counts. Both search comparisons asserted deep equality of all eight returned results, including ordering, destinations and excerpts. The first full search includes cold initialization; subsequent searches are warmer. Network distance and process initialization make these absolute times different from the live-site audit.

## Verification

Focused regression coverage includes ordered/bounded media reads, released file handles, missing/corrupt/retired media, manifest deletion, publication withdrawal, search excerpts, repeated document IDs, media storage/ranges, saved wording arriving during streaming, owner editing, and duration-only search headers.

The Home streaming test deliberately leaves the calendar unresolved, confirms the main content and accessible loading message have been sent, then resolves the calendar and checks the final content and absence of render errors.

On the pinned Next.js 16.4.6 dependency set, all 15 focused test files passed: **95 tests passed, 3 optional bucket-write integration tests skipped** because no disposable test bucket was configured. The separate connected benchmarks exercised real bucket reads. TypeScript, targeted ESLint and `git diff --check` pass.

The optimized Next.js production build passed, including TypeScript and all 451 generated routes. This was the framework build, not the full release pipeline that restores/verifies every media artifact.

A Chromium smoke test against the built app and connected services passed: Home returned 200, the calendar completed, keyboard focus reached the skip link, and there were no browser exceptions or failed requests. A warm search returned eight valid results in 5,198 ms: library 2.8 ms, supplements 5,153.4 ms, ranking 31.0 ms. These remain local measurements. See [browser receipt](browser-smoke-2026-11-26.json).

## Reproduce

Run the focused suites through `npm test`. For a connected read-only comparison, supply the existing runtime database and media-storage settings securely in the process environment, then run:

```text
node scripts/performance/compare-search.mjs 7cda443f
```

The script creates baseline modules and its test under ignored `.data/search-benchmark/`, compares both implementations, alternates execution order between the two fixed queries, and writes durations/counts to `.data/search-benchmark/results.json`. It does not call AI, modify application data or save credentials.

## Follow-up after deployment

Use `Server-Timing` to verify search timings from the application host and test a small concurrent workload. The remaining connected-search cost is primarily supplemental storage reads, followed by library preparation. A publication-versioned index could reduce that further, but should be designed with cross-process withdrawal and media-deletion invalidation before extending caching.

The two saved-edit formats have not been merged: their matching rules and stored data differ. This change removes unnecessary reader-side work without migrating or discarding either format. Broader JavaScript splitting should follow bundle profiling; the earlier desktop audit did not identify sustained main-thread blocking.
